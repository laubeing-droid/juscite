# 合入纪律

本页只讲一件事：**什么算「可以合进 main」**。细节命令与发布步骤见[快速上手](getting-started.md)和（合入后）[开发与发布流程](dev-release.md)。

## 硬门槛（本机）

**本机 `ci_gate` 为硬门槛。** 在仓库根目录，下面两条都必须 **退出码 0**，缺一条都不算过关：

```bash
pnpm typecheck
node tools/bridge/ci_gate.mjs fast
```

- `typecheck`：工作区 TypeScript 类型检查。
- `ci_gate fast`：桥语法、UI 合同测试、桥 e2e、合成自测、品牌检查等（见 `tools/bridge/ci_gate.mjs` 文件头说明）。日志落在 `.local/ci-gate-logs/`，不入库。

改到持久化、基础壳升级、Windows 安装包等面时，在 PR 里另写本机还跑了 `persist` / `upgrade` / `package` 中的哪几条；**日常合入仍以 `typecheck` + `fast` 为底线**，加跑项不能代替这两条。

## 什么不能当合入证明

仓库里 **没有** `.github/workflows`，GitHub Actions 上的检查项为空。

因此：

- **不要**在 PR 或合入说明里写「GitHub CI 已通过」「Checks 全绿」之类的话——目前没有这项远程结论。
- **不要**用 PR 页面上空的检查列表当成「默认通过」。
- **只有**你本机跑完、退出码为 0 的门禁，才是这次改动的合入依据。

远程 CI 以后接上时，会改流程文档并补上工作流；在那之前，仍以本机门禁为准。

## 合入前自检（人话清单）

- [ ] 我在本机跑过 `pnpm typecheck`，退出码 0
- [ ] 我在本机跑过 `node tools/bridge/ci_gate.mjs fast`，退出码 0
- [ ] PR 描述里写清楚跑了什么；没跑的没写「已通过」
- [ ] 没有拿「GitHub CI」当挡箭牌或证明

维护者合入 PR 时，同样认本机硬门槛；合入后在更新过的 `main` 上再跑一遍上述两条，避免「只在分支上绿、合进去没复验」。
